== Introduction and Goals

This document describes the Crawl-Roster application,
a plattform for the Dragons Guild Bern (DGB) to manage and organize their events.

The Crawl-Roster is a companion app to the Discord server/guild the DGB uses.

* It provides an integration and plattform to create and manage events and the tables / player-groups per event.
* Allows the users to manage a minimal profile that supports the even and group organization i.e. what languages they speek, system experiance.
* Uses a custom Discord-Bot for a seamless integration in the Discord client to proved the features without the need to switch to a web GUI.

=== Requirements Overview

The Craw-Roster integrates with Discord via a Discord-Bot and provides the following functionality with the bot and the web GUI.

* Management of a guild / a Discord server - the organizations specific permissions and roles that are needed for the app.
* Management of the events, the tables/groups per event.
* Synchronization between the app and the Discord Server. Events and groups per are available in the web and in Discord as event-channels where users organize themselves and their tables.
* Users don’t need a dedicated account for the app, Discord is used as IDP and the application integrates via OIDC.

=== Quality Goals

==== Functional Suitability / Flexibility

The app should support multiple guild (multi-tenancy) with managing and organizing the events.
For this the plattform needs to provide the required functionality and behavior as expected from it’s users.

Interactions should be clear for the users, behavior and actions should be clear and understandable as the users have different levels of know-how regarding the plattform, the organization and to technology.

The plattform should provide the users, admins and organizers a certain amount of flexibility
as last minute changes are a common occurrence and the plattform should not hinder the process.

==== Maintainability

The application is build and maintained by a small group of devs in their spare time.
There is a small budget in time and material so the plattform should be easy to maintain,
avoid complexity when possible and not use "obscure" or experimental technology.

==== Reliability

The application is build and maintained by a small group of devs in their spare time.
So the app should observ a zero to low failure rate, provide fault tolerance when discord API is not available
and require zero to low dev support as the possible "SLA" is best effort.
